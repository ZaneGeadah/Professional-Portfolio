GT Movies Store

A full-stack movie storefront, built end-to-end in Django around 21 user stories covering shoppers, reviewers, and store administrators.

GT Movies Store is a web app where a visitor can register an account, log in, and browse a searchable catalog of movies. From a movie's detail page they can read what other users thought of it, add copies to a shopping cart, and check out; a separate orders page keeps a running history of what they've purchased. Registered users can also write their own reviews, and edit or delete them later, while a report action lets anyone flag a review that shouldn't be there. Behind the storefront, a Django admin console gives an administrator full control to create, update, or delete users, movies, reviews, and orders.

I built the whole thing myself using Django's model-view-template pattern: Python models define the movies, reviews, cart items, and orders; views and URL routes connect user actions to that data; and templates render the pages a shopper actually sees. The layout is responsive, so the store works the same way from a laptop browser or a phone.

Building it helped me understand how the pages a user interacts with connect to the Python code and stored data behind them — and gave me a much clearer sense of how a real product gets built one working feature at a time.

PROCESS & REFLECTION

Learning the “why” behind the code.

01 / METHODOLOGY

Build with understanding, one feature at a time.

I followed Django 5 for the Impatient: Learn the Core Concepts of Django to Develop Python Web Applications by Daniel Correa and Greg Lim, and used it to structure my build order around Django's model-view-template pattern: data models first (movies, reviews, cart items, orders), then the views and URL routes that connect user actions to that data, then the templates that render each page.

What I loved about the book was how it explained why we wrote each line of code and made each decision, not just what to type. I built feature by feature — accounts, then catalog and search, then reviews, then cart and checkout — testing each one in the browser before starting the next, so a bug almost always traced back to whatever I'd just added.

02 / NAVIGATING ISSUES

Research, retrace, repair.

When I ran into a problem, I looked it up online and went back through the book’s steps, comparing them line by line against my own code to find where I’d diverged, then checked that my change actually fixed the issue instead of just masking it.

One recurring challenge was copying code from the book into VS Code — the pasted code sometimes introduced syntax or formatting errors. Working through those problems taught me to read the code carefully rather than assume that copying it meant it would work, and to isolate whichever feature was failing so I could test it on its own before touching anything else.

03 / SHARING THE RESULT

From my laptop to the web.

I committed my progress to GitHub as I went, which gave me a working checkpoint to fall back on whenever a change broke something, and eventually deployed the Django application through PythonAnywhere.

My biggest takeaway was that following a process still requires active problem-solving. Understanding each step made it easier to figure out what went wrong, and gave me more confidence connecting the frontend a user sees to the Python and database logic behind it.
